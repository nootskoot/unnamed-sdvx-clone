# Tests.Audio/baseline.md

Measured baseline for the clone's effect DSPs against the ksmaudio reference
transcriptions, taken before the audit's fixes were accepted and re-taken
against the working tree that carries them.

**Every number below was produced by a built binary, not estimated.** Source
for each row is `Tests.Audio/baseline/build/{before,after}.csv`, generated by
`Tests.Audio/baseline/build_baseline.sh` and formatted by
`Tests.Audio/baseline/make_baseline.py`.

## Method

`Audio_Impl::Mix` decodes a whole block and only then runs the DSP chain, and
`AudioStreamBase::Process` has already advanced the stream position past that
block. The harness reproduces the ordering exactly: before every
`ProcessDSPs` call it sets the stream position to the END of the block and,
when the `AudioBase` under test has the field, `blockStartSample` to the START
of the block. So the before/after difference in the clock tables is the
defect and the fix, not a modelling choice.

Metric definitions:

1. **firstNonZero** - frames from the start of the measured period to the
   first frame whose gain differs from 0.
2. **openFrames** - frames at full gain (>= 0.999) in one period.
3. **releaseFrames** - partial-gain frames after the last full-gain frame.
4. **riseFrames** - partial-gain frames before the first full-gain frame.
5. **energyDb** - `10*log10(mean(gain^2))` over one period, so a gate that is
   open half the time reads about -3 dB.
6. **repeatNDb** - peak of the Nth echo repeat, relative to the unit impulse.
7. **outRmsDb** - output RMS against input RMS for a continuous 1 kHz tone.

Limits: this renders DSPs, not songs. It cannot say how a chart is parsed or
what route it takes. Chart-level deltas belong to `Tests.Audio/report.md`.

## 1. Block clock

`DSP::GetCurrentSample()` during `ProcessDSPs`: what a DSP thinks the current
frame is, against the block actually being modified.

| Call | Block starts at | before | after |
|---|---|---|---|
| `Process` #0 | 0 | **384** | 0 |
| `Process` #1 | 384 | **768** | 384 |
| `Process` #2 | 768 | **1152** | 768 |
| first call after attaching 1 s in | 44100 | **44484** | 44100 |

Before, every DSP reads exactly one block ahead (384 frames, 8.71 ms). After,
it reads the block start.

## 2. Effect onset against `startTime`

A gate with `startTime = 1000 ms`, constant input, rate 0.50. An open gate
multiplies by 1.0, so the observable event is the first frame it closes on.

| Quantity | before | after | expected |
|---|---|---|---|
| first closed frame | 45205 | 45753 | 45753 |
| frames early | **548** | 0 | 0 |

Before, the gate acts **548 frames (12.4 ms) early**. That number
decomposes exactly into the two defects this document measures separately: the
one-block clock (384 frames) plus the old gate's ramp, which began
164 frames into its own open window instead of at the end of it
(halfway 1653 minus the 1489 open frames in section 4). After, onset
lands on the authored frame.

## 3. Effect window (`endTime`)

A DSP with `startTime = 1000 ms` and `endTime = 1500 ms`, rendered over 2000 ms
of blocks.

| Quantity | before | after |
|---|---|---|
| frames processed before `startTime` | 43776 | 10752 |
| frames processed after `endTime` | **21786** | 0 |
| total frames processed | 87936 | 33126 |
| authored length | 22050 | same |
| `endTime == 0` stays unbounded | 87936 | 87936 |

Before, a hold keeps rendering for the whole 2 s render, 21786 frames
(0.49 s) of it after its authored end. After, zero frames
after `endTime`.

After, the DSP is first processed 10752 frames
(244 ms) before its `startTime`, which is the 250 ms
`startSlack` in `AudioBase::ProcessDSPs`: a hold is created on the game tick
that reaches its start, so its start is already behind the render cursor and
the bound must not turn into a delay. A DSP scheduled further ahead than the
slack is still silent until its window opens.

## 4. Gate envelope

One steady-state period. `after` is compared with the reference transcription
of `ksmaudio` `GateDSP`, which is driven from the same signal.

| Case | Period (frames) | Open frames before / after / ref | Release before / after / ref | Energy dB before / after / ref | Level recovered |
|---|---|---|---|---|---|
| 200 BPM, 1/16, rate 0.50 | 3307 | 1489 / 1653 / 1653 | 328 / 12 / 12 | -3.16 / -3.00 / -3.00 | +0.16 dB |
| 200 BPM, 1/16, rate 0.75 | 3307 | 2316 / 2480 / 2480 | 328 / 12 / 12 | -1.35 / -1.24 / -1.24 | +0.10 dB |
| 200 BPM, 1/8, rate 0.50 | 6615 | 2978 / 3307 / 3307 | 658 / 12 / 12 | -3.16 / -3.01 / -3.01 | +0.15 dB |
| 150 BPM, 1/16, rate 0.25 | 4410 | 883 / 1102 / 1102 | 438 / 12 / 12 | -6.32 / -6.01 / -6.01 | +0.31 dB |
| 200 BPM, 1/32, rate 0.50 | 1653 | 745 / 826 / 826 | 162 / 12 / 12 | -3.16 / -2.99 / -2.99 | +0.17 dB |
| 200 BPM, 1/16, rate 0.05 | 3307 | 84 / 165 / 165 | 162 / 12 / 12 | -13.81 / -12.92 / -12.92 | +0.89 dB |

Reading it:

1. **The after column matches the reference exactly**, to the printed
   precision, on every case. The gate arithmetic is now the same arithmetic.
2. Before, the release was `min(5% of the period, half the open window, half
   the closed window)` frames, spent *inside* the open window and followed by
   a rise at the end of the period. That is why `openFrames` is short and
   `releaseFrames` is long: the gate was ramping where it should have been
   fully open, then ramping again into the next period instead of staying shut.
3. The per-period level cost is small at wide gates and largest at narrow ones,
   where the ramp is nearly as wide as the open window itself. This is the
   'brief effects feel weak' measurement.

At the narrowest case the gate is **0.89 dB louder per period** after the fix, and
its open window goes from 84 to 165 frames: it was losing
half of every open window to its own ramp.

Peak gain is 0.00 dB for every gate case in both builds, because every case
reaches full gain somewhere inside its window. Peak gain therefore does not
discriminate the gate defect; the whole defect is in the shape and duration of
the open window. It does discriminate echo (section 5, repeat levels) and the
biquad (section 7, `gainDb`).

## 5. Echo: level, decay and tail

Single-frame impulse, 24 repeats measured.

| Case | Repeat 1 dB before / after / ref | Decay per repeat dB before / after / ref | Repeats to -60 dB before / after / ref | Tail seconds before / after / ref |
|---|---|---|---|---|
| 150 ms, feedback 0.60, mix 0.50 | -10.46 / -6.02 / -10.46 | -10.46 / -4.44 / -4.44 | 6 / 14 / 13 | 0.90 / 2.10 / 1.95 |
| 150 ms, feedback 0.60, mix 1.00 | -4.44 / 0.00 / -4.44 | -4.44 / -4.44 / -4.44 | 14 / 15 / 14 | 2.10 / 2.25 / 2.10 |
| 75 ms, feedback 0.80, mix 0.50 | -7.96 / -6.02 / -7.96 | -7.96 / -1.94 / -1.94 | 8 / > 24 / > 24 | 0.60 / > 24 loops / > 24 loops |
| 300 ms, feedback 0.40, mix 0.70 | -11.06 / -3.10 / -11.06 | -11.06 / -7.96 / -7.96 | 6 / 9 / 8 | 1.80 / 2.70 / 2.40 |

Reading it:

1. Before, the decay per repeat was `feedback * mix`. At mix 0.50 with feedback
   0.60 that is 0.30 per repeat, **-10.46 dB instead of the reference's -4.44**,
   and the tail reached -60 dB after 6 repeats instead of 13. The echo ended at
   **46% of its intended length**.
2. After, the decay per repeat is the reference's on every case, and mix no
   longer appears in the law. What still differs is the absolute level of each
   repeat: upstream multiplies the loop by `feedback` at the loop boundary *and*
   tapers each loop by `(1.25L - k)/1.25L`, so its first repeat already reads
   0.6; the clone's reads 1.0 at mix 1. That is a fade-out taper the clone has
   not ported, not a feedback error, and section 8 does not assert on it.
3. At mix 1.00 the before numbers were already identical to the reference,
   which isolates the old defect to the mix and feedback path rather than the
   delay length.

## 6. Echo: does the dry signal survive

Continuous 1 kHz tone, output RMS against input RMS. An impulse cannot test
this, because after the first frame the dry input is zero anyway.

| Case | before | after |
|---|---|---|
| mix 0.00 (must be transparent) | **silence** | +0.00 dB |
| mix 0.50 | **-21.09 dB** | +3.57 dB |
| mix 1.00 | **-11.93 dB** | +6.14 dB |

Before, **mix 0 silenced the channel completely** and mix 0.50 came out 21 dB
below the input. That is the loudest single defect in this baseline: an echo
that is supposed to be a subtle 50% blend instead removed most of the signal.
After, mix 0 is bit-transparent (0.00 dB). At mix 0.50 the level sits *above*
unity because 150 ms is exactly 150 cycles of a 1 kHz tone, so the repeats sum
in phase with the dry signal instead of cancelling it; the same effect at a
frequency that is not an exact multiple would read differently. That is the
expected behaviour of a feedback delay, not a gain error.

## 7. Biquad mix law

Steady-state gain through `BQFDSP` for a sine at the probe frequency.

| Filter | Probe | Mix | before | after |
|---|---|---|---|---|
| peaking +6 dB @1 kHz, Q4 | 1 kHz | 0.00 | **6.00 dB** | 0.00 dB |
| peaking +6 dB @1 kHz, Q4 | 1 kHz | 0.50 | **6.00 dB** | 3.51 dB |
| peaking +6 dB @1 kHz, Q4 | 1 kHz | 1.00 | **6.00 dB** | 6.00 dB |
| lowpass 800 Hz Q0.7 @4 kHz | 4 kHz | 0.00 | **-28.43 dB** | 0.00 dB |
| lowpass 800 Hz Q0.7 @4 kHz | 4 kHz | 0.50 | **-28.43 dB** | -6.34 dB |
| highpass 8 kHz Q0.7 @500 Hz | 500 Hz | 0.00 | **-50.20 dB** | 0.00 dB |
| highpass 8 kHz Q0.7 @500 Hz | 500 Hz | 0.50 | **-50.20 dB** | -6.05 dB |

Before, `mix` was ignored entirely: the filter ran at full depth at every mix
value, so mix 0 applied +6.00 dB of peaking, -28.43 dB of low-pass and
-50.20 dB of high-pass where the dry signal was asked for. After, mix 0 is
0.00 dB and mix 0.50 of the +6 dB peaking lands at +3.51 dB, which is the
linear blend `dry + (wet - dry) * mix` evaluated at the peak.

This is why partial-mix laser filters read as too strong or too dull instead of
as a blend, and why callers folded mix into gain and Q to compensate.

## 8. Thresholds for `Tests.Audio/src/AuditTests.cpp`

These are the assertions these measurements support. Each is a range, not a
value, so build-to-build float noise cannot fail the suite.

1. Block clock: at the first frame of every processed block,
   `GetCurrentSample() == blockStartSample`, for a stream starting at 0 and
   for one starting at 44100.
2. Onset: a gate with `startTime = 1000 ms` first changes its output at frame
   44100 + `halfway`, within +/- 0 frames.
3. Window: a DSP with `endTime = 1500 ms` modifies no frame at or after
   frame 66150 (1500 ms), and `endTime == 0` is unbounded.
4. Gate: `openFrames == floor(period * rate)` and `releaseFrames == 12` for
   every case where `numNonZeroFrames > 12`; `releaseFrames == 0` when it is
   12 or fewer; no partial-gain frames anywhere else in the period.
5. Gate energy: `energyDb` within 0.01 dB of the reference for all six cases
   (measured: identical to 6 decimals).
6. Echo decay: `decayPerRepeatDb == 20*log10(feedback)` within 0.01 dB, for
   mix 0.25, 0.50 and 1.00. Mix must not appear in the law.
7. Echo transparency: `outRmsDb == 0.00 +/- 0.01` at mix 0 with a continuous
   tone, for feedback 0.3, 0.6 and 0.9.
8. Biquad: `gainDb == 0.00 +/- 0.01` at mix 0 for peaking, low-pass and
   high-pass, and `gainDb` at mix 1 equal to the mix-0 build's full-depth
   value within 0.01 dB.

## 9. What these numbers do not cover

1. **No chart was rendered.** Both attached charts are KSH v1 event lists;
   this harness renders DSPs. `Tests.Audio/report.md` owns the chart-level
   before/after and the spectrograms.
2. **The KSON measure clock is untested here.** `GateDSP::SetMeasureTimes` is
   not exercised by any case above; a synthetic measure list belongs in the
   regression suite, not the baseline.
3. **Retrigger is not in this table.** It shares the reference class with echo
   but has its own trigger path, and it was not measured before the fixes
   landed. It should get its own baseline row if the retrigger path changes.
4. **`startSlack` only shows up in section 3.** `AudioBase::ProcessDSPs`
   allows a DSP to start up to 250 ms before its `startTime`, so a hold created
   on a late game tick still lands on its first frame. Section 3 measures that
   as 10,752 frames (244 ms) of early processing; the onset table in section 2
   cannot see it, because that gate is created before the render starts. A case
   with a simulated calibration offset should be added if the slack is revisited.
5. **No release fade at `endTime`.** The window table measures frames
   processed, not whether the cut clicks. A resonant filter cut mid-ring is
   the case to check by ear.
